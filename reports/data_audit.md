# Data Audit

Generated by `python -m src.data.data_audit`. Covers the checks done before any modeling started: label balance, missing/malformed fields, duplicate risk, and target leakage.

## Label distribution

| Label | Train | Validation | Train % | Val % |
|---|---:|---:|---:|---:|
| Read | 14084 | 2817 | 63.6% | 63.6% |
| Write | 5433 | 1087 | 24.5% | 24.5% |
| Execute | 1175 | 235 | 5.3% | 5.3% |
| Destructive | 1264 | 253 | 5.7% | 5.7% |
| Financial | 111 | 22 | 0.5% | 0.5% |
| Other | 76 | 15 | 0.3% | 0.3% |

`Read` outnumbers `Other`, the rarest class, by roughly **185x** in training data, and `Financial` plus `Other` combined are under 1% of rows. This is a long-tailed, imbalanced 6-way problem, so accuracy alone would be misleading. Macro F1 as the primary metric (per the task spec) is the right call.

### Cross-split overlap (leakage check)

| Pair | Shared `server_slug`s | Shared (name, description) content |
|---|---:|---:|
| train_vs_validation | 0 | 315 |
| train_vs_test | 0 | 270 |
| validation_vs_test | 0 | 56 |

`server_slug` overlap is 0 across every split pair, so the provided StratifiedGroupKFold split is doing what it should: grouping by server stops a model from memorizing a server's house style instead of learning the actual task. The non-zero content-overlap numbers above aren't a split bug though. Different MCP servers sometimes ship near-identical generic tools (e.g. a boilerplate `list_files` wrapper), and that shows up as overlapping text even with zero server overlap. Worth flagging as a residual risk: validation/test scores may be a little optimistic for the subset of tools that have a lookalike in training data.

## Target leakage in `servers_public.jsonl`

Scanned 2031 server-level rows for the six label words appearing verbatim in the server name/description (this file's stated purpose is server metadata with direct category labels removed, so this checks that claim actually holds). 172 rows contain one of the words, but only as ordinary English in marketing copy ("read and write files", "execute complex workflows") describing what the server does broadly, never as a structured label. `servers_public.jsonl` isn't joined into the training text anyway (see Text representation below), so this is a non-issue for the current pipeline either way - the scan just makes that decision verifiable instead of assumed.

## Text representation

Each record is rendered as a single text block (`src/data/schema.py:build_input_text`):

```
Tool name: <name>
Description: <description, whitespace-normalized, truncated to 900 chars>
Parameters:
- <param> (<type>, required|optional)[ enum[...]]: <short param description>
- ...
```

**Why this shape:**

- `name` and `description` carry most of the signal (verbs like *delete*, *transfer*, *list*, *execute* are strongly predictive of the action category), so they're kept close to verbatim.
- `input_schema` is not dumped as raw JSON. Raw JSON burns tokens on punctuation, and schema depth varies a lot, from `{}` to nested `oneOf`/`anyOf` branches. Flattening to `name (type, required): description` keeps the useful signal (a `confirm: boolean` parameter is a strong `Destructive` cue, an `amount`/`currency` pair is a strong `Financial` cue) while capping length at 12 rendered parameters and 140 characters per parameter description.
- `server_slug` and `servers_public.jsonl` metadata are deliberately left out of the model input. A model that can see server-level description text can shortcut to "which server is this" instead of "what does this tool do", and that kind of proxy signal generalizes badly to servers the model has never seen, which is the actual deployment scenario.
- The same `build_input_text` function feeds both the TF-IDF baseline and the SLM, so any macro F1 gap between them comes from the modeling approach, not from one of them getting a richer input.

## Input length

| Split | Mean chars | Max chars |
|---|---:|---:|
| train | 396.2 | 3097 |
| validation | 457.8 | 2665 |
| test | 380.9 | 2725 |

This is what the SLM's max sequence length (README.md, Decisions -> Sequence length) is based on. A small number of tools have long, example-heavy descriptions (some MCP servers embed multi-paragraph usage examples, e.g. `firecrawl_crawl`) that end up truncated, but the truncation point falls well past the name/description/first-parameters prefix where most of the signal already lives.
